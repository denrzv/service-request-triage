# FEATURE-005: Jev Baseline Benchmark
Status: PRD_READY

Issue: https://github.com/denrzv/service-request-triage/issues/5 (depends on FEATURE-002, FEATURE-003 and
FEATURE-004, all merged).
Branch: `claude/feature-005-development-vrzpb2` (session-assigned branch; one ticket per branch).

## Context / Problem
ADR-009 requires measuring Jev **before** adding graph or LLM complexity (milestone M1). FEATURE-002 delivered a
typed Jev HTTP adapter, FEATURE-003 a pure Policy Engine with an explicitly uncalibrated policy `v1`, and FEATURE-004
a frozen 240-case English goldset (dev 165 / held-out test 75). Nothing yet connects them: there is no versioned
Jev question set for triage, no mapping from Jev answers to a `SemanticAssessment`, no rules-only comparison, no
metrics and no threshold evidence. FEATURE-006/007 need that evidence and the question set; FEATURE-013 needs a
comparable baseline.

## Goals
- A versioned triage question set for Jev (three Choice dimensions plus Noul signals, including a Companion Noul
  for taxonomy fit) and a strict mapper from `JevClassificationResult` to `SemanticAssessment`, reusable by
  FEATURE-006/007.
- A JUnit benchmark harness that runs two baselines through the **same** Policy Engine and policy `v1`, with no
  StateGraph and no DeepSeek fallback:
  - `RULES_ONLY`: a small deterministic keyword assessor;
  - `JEV_ONLY`: Jev judgments via `JevClassificationPort`.
- Metrics per split: macro-F1 for formal SR type (plus intent and domain), complaint recall and false-negative
  rate, formal-type confusion matrix, route distribution, abstention and review rates, wrong auto-route rate,
  selective accuracy vs coverage, out-of-taxonomy success, provider error count.
- Separate capture of Choice selected value, top probability, confidence and top-two margin per dimension, and of
  every Noul signal (Companion Noul `taxonomy_fit` reported on its own).
- Threshold candidate exploration on the **development/calibration split only**, with one held-out check of the
  chosen candidates.
- Token, latency and cost estimates with the requested alias, the resolved model and the question-set version.
- English Markdown report, JSON metrics and CSV files persisted under `reports/evaluation/<runId>/`, including
  dataset hashes and limitations.
- Offline operation without an API key (replay of recorded Jev responses) and an opt-in live run.

## Non-goals
- StateGraph, DeepSeek/LLM-only baseline, hybrid routing (FEATURE-006/008/009/013).
- Publishing a calibrated policy file or changing policy `v1` thresholds (FEATURE-007 owns calibrated policy).
- Hierarchical (two-stage) Jev classification (optional later experiment, ADR open decision 4).
- REST API, `IncomingCustomerRequest`, `ClassificationModelPort` (FEATURE-006/012).
- Changing the goldset or its labels.

## Users & Roles
- Architects deciding whether Jev is suitable at all before graph work (milestone M1).
- Policy maintainers (FEATURE-007) who need threshold evidence from the calibration split.
- Evaluators (FEATURE-013) who need a reproducible, comparable baseline.

## User Stories
- As an architect, I want Jev-only and rules-only results on the same goldset and policy so that I can see whether
  Jev adds value beyond simple rules.
- As a policy maintainer, I want coverage vs wrong-auto-route curves per threshold on the calibration split so that
  I can propose candidate thresholds without touching held-out labels.
- As an evaluator, I want the committed results to be regenerated byte-for-byte offline from recorded responses
  and dataset hashes so that the baseline is reproducible in CI without credentials.

## Main Scenarios
1. Default `./mvnw verify`: unit tests plus an offline reproducibility test that replays the committed Jev
   recordings and the rules-only baseline over the goldset and asserts the regenerated artifacts equal the
   committed report files.
2. Opt-in live run (`JEV_BENCHMARK_LIVE=true`, `JEV_API_KEY`): one Jev call per goldset case (both splits), raw
   typed answers recorded, report written to `reports/evaluation/<runId>/`.
3. Maintainer reads `report.md`: metrics per mode and split, signal summaries, threshold sweep and candidates,
   cost/latency, limitations.

## Edge Scenarios
1. Jev unavailable / client error / protocol error for a case: case decided by `modelUnavailable` (`HUMAN_REVIEW`,
   `MODEL_UNAVAILABLE`), counted as a provider error, recorded and replayed as an error; never a default confidence.
2. Jev answer missing, of the wrong type, or with unknown/missing choice keys: mapper raises
   `JevProtocolException` (same safe path).
3. Replay recording missing for a message, recorded message hash mismatch, or dataset hash differing from the
   manifest: the run fails loudly instead of silently re-labelling.
4. Threshold exploration given any held-out case: rejected by construction.
5. Live run with more cases than the configured call budget: refused before the first call.
6. Prices not configured: cost reported as "not estimated", tokens still reported.
7. Policy `v1` concerns (multi-intent, low confidence, near-tie) under a candidate policy: become `HUMAN_REVIEW`
   because the baseline has no investigation budget left (no LLM fallback).

## Acceptance Criteria
(Mirrors issue #5.)
- AC1: A standalone JUnit harness runs rules-only and Jev-only classifications.
- AC2: Offline mocked/replayed responses usable without an API key; live Jev run is opt-in.
- AC3: Metrics: macro-F1 per formal type, complaint recall, confusion matrix, abstention and out-of-taxonomy success.
- AC4: Choice probabilities/confidence and Companion Noul signals captured separately.
- AC5: Initial threshold candidates explored on the calibration split only; no tuning on held-out test labels.
- AC6: Tokens/latency/cost estimates reported with the actual model alias and question-set version.
- AC7: English Markdown results and CSV persisted with dataset hash and limitations.

## Non-functional requirements
- Security: API key from environment only; never logged or written to reports. Only goldset `message` and
  `channel` are sent to Jev; labels, rationale, stratum and case IDs are never sent.
- Privacy/data protection: synthetic English data only; reports contain case IDs, predictions and provider signals,
  not messages or gold labels per case.
- Reliability: offline default build needs no network or credentials; live run uses the existing adapter's
  timeouts and bounded retries plus a total call budget.
- Performance/scale: offline benchmark completes in seconds; live run is 240 sequential calls.
- Observability: per-case CSV, run metadata (alias, resolved model, question-set, taxonomy and policy versions,
  dataset hashes, price source).
- Compatibility: Java 25, Boot 3.5.x, no new dependencies; runtime artifact unchanged except the question set and
  mapper.

## Data considerations
- Identifiers: `runId` (directory name), goldset `caseId` as the join key, message SHA-256 as the replay key.
- Sensitive data: none; recordings hold Jev answers and usage only.
- Retention/lifecycle: committed runs are immutable evidence; a new run uses a new `runId`.

## Constraints & Assumptions
- Baselines use policy `v1` unchanged and the engine with the investigation budget exhausted, so no route can be
  `LLM_INVESTIGATION`.
- Pricing per the TypeSafe Models page (retrieved 2026-11-21): USD 0.042 per million input tokens, output tokens
  free; passed as run parameters, never embedded in runtime code or policy.
- The keyword rules are authored from taxonomy descriptions and the development split only.
- The live Jev endpoint is reachable from this environment (smoke call resolved `jev-1.14.0`).

## Risks
- A 240-case single-author synthetic goldset gives wide confidence intervals; results are indicative only.
- `jev-latest` moves; the resolved model is recorded and replay pins the recorded answers.
- Rules authored by the same author as the labels may be optimistic; documented as a limitation.
